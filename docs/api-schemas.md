# API Schemas and Data Contracts

## Overview

`src/aie_estimator/schemas/estimations.py` defines the domain data models and validation perimeter for the estimation service. Built with Pydantic v2, these schemas enforce strict request validation before execution and guarantee deterministic response contracts across all LLM providers.

The schemas govern three functional phases of the estimation lifecycle:
1. **Request Intake (`EstimationRequest`)**: Ingestion, constraint validation, and default configuration for meeting transcript analysis.
2. **Execution & Instrumentation (`TokenUsage`)**: Token consumption accounting across single-phase and two-phase workflows.
3. **Quality & Compliance (`StructureCheck` & `EstimationResponse`)**: Level-1 deterministic structural evaluation, cache status tracking, and standardized response payload delivery.

---

## Schema Reference

### 1. `EstimationRequest`

Payload schema for `POST /api/v1/estimate`:

| Field | Type | Default | Constraints | Description |
| :--- | :--- | :--- | :--- | :--- |
| `transcription` | `str` | *(required)* | `min_length=50` | Meeting transcript containing client requirements and project scope. |
| `preprocessing` | `PreprocessingMode` | `"none"` | `"none"`, `"inline_cleaning"`, `"two_phase"` | Transcript preprocessing strategy before prompt assembly. |
| `example_format` | `ExampleFormat` | `"markdown"` | `"markdown"`, `"json"`, `"narrative"` | Serialization format used for few-shot reference examples. |
| `num_examples` | `int` | `3` | `ge=0, le=5` | Number of historical canonical examples injected into the prompt. |
| `use_examples` | `bool` | `True` | — | Master toggle for few-shot examples (overrides `num_examples` when `False`). |
| `model` | `str \| None` | `settings.llm_model` | Must exist in `SUPPORTED_MODELS` | Target LLM model override; validated via `@field_validator`. |
| `max_tokens` | `int` | `4000` | `gt=0, le=16000` | Maximum token budget for the estimation completion. |
| `thinking_budget` | `int \| None` | `None` | `ge=0, le=16000` | Extended thinking token budget (Anthropic only; ignored for OpenAI). |
| `evaluate` | `bool` | `True` | — | When `True`, triggers Level-1 structural evaluation (`StructureCheck`). |

### 2. `EstimationResponse`

Unified response schema returned by `POST /api/v1/estimate`:

| Field | Type | Description |
| :--- | :--- | :--- |
| `estimation` | `str` | Complete generated software project estimation markdown text. |
| `model` | `str` | Identifier of the model that produced the estimation (e.g. `gpt-4o-mini`). |
| `provider` | `str` | Upstream provider invoked (`openai` or `anthropic`). |
| `usage` | `TokenUsage` | Breakdown of input, output, and preprocessing token consumption. |
| `finish_reason` | `str` | Upstream completion reason reported by the provider (`stop`, `end_turn`, etc.). |
| `latency_ms` | `int` | Server-side total turnaround latency in milliseconds. |
| `cache_hit` | `bool` | `True` when served directly from Redis exact-match cache; `False` on API invocation. |
| `preprocessing` | `PreprocessingMode` | Active preprocessing strategy utilized for the request. |
| `extracted_requirements` | `str \| None` | Clean requirements produced during Phase 1 when `preprocessing="two_phase"`; `None` otherwise. |
| `validation` | `StructureCheck \| None` | Structural evaluation result when `evaluate=True`; `None` when evaluation is disabled. |

### 3. Supporting Sub-Schemas

#### `TokenUsage`
Tracks end-to-end token consumption across multi-phase workflows:
- `input_tokens` (`int`): Main prompt input tokens.
- `output_tokens` (`int`): Estimation completion tokens.
- `total_tokens` (`int`): Sum of main call input and output tokens.
- `preprocessing_input_tokens` (`int`, default `0`): Phase-1 requirement extraction input tokens.
- `preprocessing_output_tokens` (`int`, default `0`): Phase-1 requirement extraction completion tokens.

#### `StructureCheck`
Level-1 structural verification generated by `src/aie_estimator/services/evaluation.py`:
- `has_title` (`bool`): Matches Markdown H2 heading (`## ...`).
- `has_breakdown_table` (`bool`): Matches task breakdown table with `Task | Hours | Cost` header.
- `has_totals_section` (`bool`): Detects both `Total hours` and `Total cost` declarations.
- `has_team_section` (`bool`): Verifies team composition recommendations.
- `has_duration_section` (`bool`): Verifies estimated delivery duration.
- `declared_total_hours` (`int | None`): Declared total hours parsed from summary.
- `sum_row_hours` (`int | None`): Sum of individual task row hours.
- `hours_match` (`bool | None`): `True` if `abs(sum_row_hours - declared_total_hours) <= 1`.
- `declared_total_cost` (`float | None`): Declared total cost in EUR.
- `sum_row_cost` (`float | None`): Sum of individual task row costs in EUR.
- `cost_match` (`bool | None`): `True` if discrepancy between row sums and declared cost is `<= 2%`.
- `finish_reason_ok` (`bool`): `True` if provider stop reason is `"stop"` or `"end_turn"`.
- `score` (`float`): Normalized structural compliance score from `0.0` to `1.0`.
- `issues` (`list[str]`): Descriptive list of failed structural criteria.

### 2. Two-Phase Preprocessing with Extended Thinking

Request overriding preprocessing strategy, model, and thinking budget:

```json
{
  "transcription": "Raw noisy transcript with small talk, interruptions, and requirements...",
  "preprocessing": "two_phase",
  "model": "claude-haiku-4-5-20251001",
  "thinking_budget": 2048,
  "example_format": "markdown",
  "num_examples": 2,
  "evaluate": true
}
```

In this scenario:
- Phase 1 runs `extract_requirements` to isolate clean specifications, populated in `extracted_requirements` and recorded in `preprocessing_input_tokens` / `preprocessing_output_tokens`.
- Phase 2 invokes Anthropic with extended thinking enabled, omitting `temperature` and padding `max_tokens`.
- Structural evaluation validates the final markdown format against `StructureCheck`.

## Technical Considerations

### 1. Boundary Validation vs. Upstream Failures
`EstimationRequest` uses `@field_validator("model", mode="after")` to validate requested model identifiers against `SUPPORTED_MODELS` at the API boundary. This intercepts unknown models and placeholders (e.g. Swagger default `"string"`) immediately, returning HTTP 422 Unprocessable Entity and protecting upstream vendor endpoints from invalid calls.

### 2. Pydantic Default Evaluation
`model` defaults to `get_settings().llm_model` dynamically via `validate_default=True`. This ensures requests without explicit model overrides automatically track the runtime environment's default configuration without hardcoded values.

### 3. Decoupled Structural Scoring
`StructureCheck` executes deterministically via regular expressions without secondary LLM evaluation calls. This provides zero-cost quality assertions on table headers, arithmetic consistency between individual line items and declared totals, and delivery feasibility indicators.
